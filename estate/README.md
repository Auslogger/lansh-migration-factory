# The legacy estate

LANSH's input: a realistic legacy estate for **SynthInsure**, a fictional Irish insurer selling
motor, home and travel cover from 2019 to 2025. Every job reports as of **2025-12-31**.

It has the shape Challenge 03 describes: legacy T-SQL and SAS jobs, their input data and their
expected outputs. The inputs are bronze (`stg`), and the jobs write silver (`dw`) and gold
(`rpt`) tables for finance, actuarial and claims reporting.

## Data statement

All data is **100% synthetic**, generated by `lansh estate generate` (`src/lansh/estate/generate.py`)
with seed **20251231**. Names and addresses are fictional (Faker `en_IE` plus common Irish
names); emails use the reserved `.example` domain; there are no phone numbers and no real
records. Public geography (county and town names, Eircode routing keys) is used for realism.

## Layout

| Path | What |
|---|---|
| `jobs.yaml` | Inventory of the legacy jobs: code, parameters, inputs and outputs (`lansh.contracts.EstateInventory`) |
| `data/` | The nine source extracts as Parquet (committed), `dictionary.yaml` (schema and `pii`/`protected` tags), `manifest.json` (seed, row counts, SHA-256 hashes). CSV copies go to `data/csv/` (gitignored) |
| `tsql/` | T-SQL deployment scripts, one per job; `tsql/ddl/` has the base objects and the generated source-table DDL |
| `sas/` | SAS programs, one per job |
| `golden/<JOB>/` | Golden outputs captured from the real engines: raw CSV, typed Parquet, `manifest.json`; SAS jobs also keep the exact `HEX16.` numbers, PROC CONTENTS and the redacted log. Immutable |
| `holdout/` | Sealed held-out jobs. Not opened before the factory freeze (plan step 3.11) |
| `labels/` | The answer key. **Evaluation only: factory code never reads it** (see the last section) |

The source tables hold about 232,000 rows for 20,000 customers, with claims at a realistic
frequency (paid claims come to about 64% of earned premium). They are customers (a CRM extract
with record versions), brokers, products, two policy snapshots, premium transactions, claims,
claim payments, claim reserves and exchange rates.

## Rebuilding

```bash
make data            # regenerate the extracts (byte-identical to the committed ones)
make legacy-up       # SQL Server 2022 in Docker
make load            # rebuild SynthInsureDW and load the extracts (hashes verified)
make golden          # run every job on its real engine and capture golden outputs
make legacy-verify   # rebuild from scratch and check the T-SQL golden hashes reproduce
make legacy-verify-all  # the same, plus the SAS jobs on SAS OnDemand
```

## How SAS jobs see their inputs

SAS jobs run with librefs `stg`, `dw` and `rpt` and the macro variable `&as_of`
(`'31DEC2025'd`). Source tables keep their extract `_row_seq`. A table written by a T-SQL job is
handed to SAS with `_row_seq` in **key order**: sorted by its first column, then by the others,
NULLs first. That's how a SAS `libname` read of the warehouse table sees it, and a migrated job
reading the same table must use the same order. A table written by a SAS job is read as its
native data set.

## Legacy coding style

How SynthInsure's data team wrote its ETL jobs between roughly 2012 and 2022. Every legacy job
in this estate follows it, so the estate reads like a real one. It describes **how the code
looks and runs**, not what any job computes. (The held-out author was given this section as
`STYLE.md`.)

### Every job

- **Purpose.** One job builds one output table for finance, actuarial or claims reporting.
- **Size.** 40 to 200 lines, including the header.
- **Header block.** Job name, purpose in a sentence or two, author initials, and a change log
  with dated entries (`2018-04-12  JMcK  Added broker filter (CR-1123)`). Ticket numbers and
  initials are invented.
- **Deterministic output.** The same inputs and parameters always give the same output:
  - Every ranking, `TOP`, de-duplication or "first/last row" choice orders by a unique
    tiebreaker at the end, such as an id column or `_row_seq` (the extract row number).
  - Output values never depend on how text sorts or on which of several equal rows the
    engine happens to return.
  - Business dates come from the `@AsOfDate` parameter (`&as_of` in SAS), never from
    `GETDATE()`, `SYSDATETIME()` or `today()`. The only exception is a load-timestamp audit
    column whose name says so (for example `load_ts`).
- **Full refresh.** A job rebuilds its output from scratch on every run (`TRUNCATE` and reload,
  or drop and recreate). A job that maintains history (one that is run once per batch) is
  the exception, and its header says so.
- **Magic numbers** are normal: thresholds and band edges are written inline, not looked up.
- **No dynamic SQL, no linked servers, no `xp_cmdshell`, no external files.**

### T-SQL (SQL Server 2022, database `SynthInsureDW`, collation `SQL_Latin1_General_CP1_CI_AS`)

- One deployment script per job in `estate/tsql/`, split into batches with `GO`:
  1. the header comment;
  2. the output table: `IF OBJECT_ID(N'rpt.x', N'U') IS NULL CREATE TABLE rpt.x (...)`;
  3. `CREATE OR ALTER PROCEDURE schema.usp_name @AsOfDate DATE AS BEGIN ... END`.
- Schemas: `stg` source extracts (read only), `dw` warehouse, `rpt` reporting, `etl` logging.
- Upper-case keywords, `SET NOCOUNT ON;` first, `WITH (NOLOCK)` on source reads, `#temp`
  tables for intermediate steps, table aliases, `ISNULL` rather than `COALESCE` by habit.
- Error handling: the body sits in `BEGIN TRY ... END TRY BEGIN CATCH ... END CATCH`. Log the
  start, each main step's row count (`@@ROWCOUNT`) and the end through
  `EXEC etl.usp_log_step @job_name = ..., @step_name = ..., @status = ..., @rows_affected = ...`;
  in `CATCH`, log `FAILED` with `ERROR_MESSAGE()` and `ERROR_NUMBER()`, then `THROW;`.
- Use `DATE`, `DATETIME2`, `INT`, `BIGINT`, `DECIMAL(p,s)`, `VARCHAR`, `NVARCHAR` and `CHAR`.
  Money is `DECIMAL`, never `FLOAT` or `MONEY`.

### SAS (SAS 9.4)

- One program per job in `estate/sas/`, run in batch with `options mprint;` at the top.
- Librefs `stg`, `dw` and `rpt` are assigned by the scheduler before the program runs; the
  program never assigns them itself. The reporting date arrives as the macro variable
  `&as_of` (a SAS date literal such as `'31DEC2025'd`).
- Header block in `/* ... */` with job name, purpose, author and change log.
- Lower-case code, DATA steps and PROCs (`SORT`, `SQL`, `MEANS`, `FORMAT`), `%macro`
  definitions where a block repeats, `work.` intermediate data sets, `keep=`/`drop=` options.
- Character variables have explicit lengths only where the original author bothered.
- The final output data set is written to `dw.` or `rpt.` with an explicit `keep` list.

### Not allowed anywhere

Real personal data; hard-coded passwords or connection strings; anything that reads or writes
files outside the database or the SAS librefs; anything that depends on the machine, the user
or the time of day the job happens to run.

## The answer key (`labels/`, evaluation only)

**Factory code must never read `labels/`** (AGENTS.md; enforced by
`tests/test_holdout_seal.py`). It lists every planted trap and bug, which would let the factory
mark its own homework. Only evaluation code reads it: detection scoring (step 3.7),
bug-reproduction proof (plan §15) and the gate packets.

| File | What |
|---|---|
| `labels/<JOB>.yaml` | The job's labels: every trap (with lines and whether our data arms it) and its bug. Format: `lansh.estate.labels.JobLabel` |
| `labels/checks/<JOB>.sql` or `.sas` | One check per armed semantic trap and per bug, proving it changes the result on our data |

Run a job's checks with `lansh estate checks --job T04`.

**T-SQL checks** (`checks/T04.sql`): batches separated by `GO`. Each batch is one check, introduced by

```sql
-- check: T04_BUG03_payments_fan_out
-- proves: payments are counted once per reserve row for claims with several reserves
SELECT 'T04_BUG03_payments_fan_out' AS check_id, COUNT(*) AS affected,
       CAST(SUM(...) AS NVARCHAR(200)) AS detail
FROM rpt.claims_summary AS s ...;
```

It runs in `SynthInsureDW` **after** the job, and returns exactly one row: `check_id`,
`affected` (a positive count passes) and an optional `detail`. Where possible a bug check
measures the bug's footprint **in the job's output table**, so the same check can later be run
against the migrated output to prove the bug was reproduced.

**SAS checks** (`checks/S01.sas`): a program run after the job, in a fresh SAS session with the
job's librefs (`stg`, `dw`, `rpt`) and `&as_of` assigned, so it reads the job's output tables but
not its `work.` data sets. It creates `work._lansh_checks` with variables `check_id $60`,
`affected 8` and `detail $200`, one observation per check.

**What `armed` means**

- **Semantic traps:** `armed: true` when our data makes the trap change the result. Every armed
  semantic trap has a check proving it. An occurrence our data doesn't arm is labelled
  `armed: false` with no check (it still counts for detection, as a latent risk).
- **Construct traps** (cursors, temp tables, MERGE, PIVOT, CROSS APPLY, macro loops, PROC MEANS)
  change the shape of the code, never the result by themselves, so `armed: true` simply means
  the construct is present and runs on our data. A check is optional. Running the job and
  reconciling it is their proof.
- **Detection scoring** counts a finding as a hit when it names the labelled trap at an
  overlapping line range. A suspected *defect* reported where a trap is labelled (for example
  T02's `ISNULL(broker_code, 'DIRECT-SALES')` truncation, which the change log calls a feature)
  counts as detecting that trap, not as a false positive.
